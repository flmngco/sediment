# S3 durability

`sediment` can keep a database's state of record in an S3 bucket. The
local file becomes a working copy:

* commits are uploaded to S3 in commit order: in the background
  (`durability: :async`, the default; `sync: true` waits for one
  transaction), or before each commit returns (`durability: :sync`);
* checkpoints upload a snapshot of the database file;
* opening the database on a machine without the local files restores it
  from S3;
* one writer at a time holds a lease, and a writer that loses it is fenced
  so it cannot overwrite anything.

This guide covers configuration, the guarantees, failure modes and costs.
The protocol and its correctness arguments are in
[docs/s3-durability.md](../docs/s3-durability.md).

## Quick start

```elixir
s3 = [
  bucket: "my-bucket",
  prefix: "prod/app",
  region: "eu-central-1",
  owner: "app-1"
]

# 64 hex characters, from Sediment.S3.generate_key() or `openssl rand -hex 32`
encryption = [cipher: "aegis256", key: System.fetch_env!("DATABASE_ENCRYPTION_KEY")]

# Low level
{:ok, db} = Sediment.Engine.open("/var/lib/app/app.db", s3: s3, encryption: encryption)

# DBConnection (or an Ecto repo using ecto_sediment)
{:ok, pool} =
  Sediment.start_link(database: "/var/lib/app/app.db", s3: s3, encryption: encryption)
```

The first open of an empty prefix creates the database in S3. Later opens,
on this or another machine, restore it.

S3 databases are encrypted by default: an open with `:s3` needs either an
`:encryption` key or `encryption: false`, the explicit choice to store the
database unencrypted. Without either it fails with `"s3 config: S3 databases
are encrypted by default: ..."`. See "Encryption".

> #### The S3 copy wins over the local file {: .warning}
>
> * When the prefix already holds a database, opening **replaces** the
>   local files at the path (the database file, its `-wal` and `.db-log`)
>   with the S3 state. Local changes that never reached S3 are discarded.
> * When the prefix is empty, the open creates a new, empty database. If
>   the path already holds a database with tables (for example an
>   existing SQLite file you just added `s3:` to, or the local copy of a
>   prefix that was emptied or mistyped), the open is refused with
>   `"s3 config: ... refusing to replace the local file ..."` and the file
>   is left alone. To upload that database as the prefix's first state, use
>   `Sediment.S3.import/3` (see "Importing an existing database"); to start
>   empty, move or delete the file.

With a local S3-compatible server:

```elixir
s3 = [
  bucket: "dev",
  prefix: "app",
  endpoint: "http://127.0.0.1:8333",
  access_key_id: "any",
  secret_access_key: "any"
]

# development data, stored unencrypted on purpose
{:ok, db} = Sediment.Engine.open("dev.db", s3: s3, encryption: false)
```

## Durability: async (default) or sync

`durability: :async` (the default): a commit returns as soon as it is in the
local log, like a local database, and a background uploader puts the
committed log frames into S3 in commit order, shortly after (contiguous
commits may share one object). A crash can lose the commits made since the
last upload, but never leaves a hole: what a restore finds is always a
prefix of the commit order. Other connections see a commit before it is
durable (visibility precedes durability, as with Litestream).

The upload lag is bounded: when the uploader falls behind by more than
`max_lag_ms` or `max_pending_bytes` (for example because S3 is down), new
commits wait until it catches up, so an outage doesn't silently turn into
unbounded loss.

To make a particular write durable before going on:

```elixir
# this transaction returns once it is durable in S3
Sediment.transaction(pool, fn conn -> ... end, sync: true)
Sediment.query(pool, "INSERT ...", params, sync: true)

# everything committed so far
:ok = Sediment.S3.flush(pool, 5_000)
```

Ecto: `Repo.transaction(fun, sync: true)` and `Ecto.Adapters.Sediment.s3_flush/2`.
A sync commit whose wait fails (timeout, fenced writer) returns an error
saying it is committed locally but not known to be durable: treat it like
an ambiguous commit (below). `sync: true` belongs on the outermost
transaction (or on a statement outside any): on a nested transaction, or a
statement inside one, nothing is committed yet and it does nothing.
`sync: true` waits for its own commit only (commits reach S3 in order, so
earlier ones are then durable too): a read, or a transaction that wrote
nothing, returns at once, so a repo that sets it for every operation still
reads without touching S3, even when S3 is slow, down, or after a loss.

`durability: :sync`: every commit returns only once it is stored in S3.
Nothing acknowledged is ever lost, at the price of one S3 round trip per
commit (see "Testing and measurements"). `sync: true` and `flush/2` then return at
once.

Closing (or stopping a pool) uploads what is pending first, waiting up to
`:close_timeout_ms`; call `flush/2` before stopping to know it's all there. Scripts, `mix run` and
Mix tasks end with `System.halt/1`, which closes nothing: the first S3 open
in a VM registers a `System.at_exit/1` hook that uploads every database's
pending commits before the VM exits (up to 30 s) and prints what it could
not. A VM killed outright (SIGKILL, `:erlang.halt/1`) skips it.
Pools started with `Sediment.start_link/1` wait for that on shutdown
(their `:shutdown` defaults to `Sediment.S3.shutdown_timeout/1`); pass
`shutdown: Sediment.S3.shutdown_timeout(s3_opts)` when starting
`DBConnection` yourself, or the pool may stop before the database is
closed.

`Sediment.S3.info/1` reports the durability mode, what is not yet
uploaded (`pending_bytes`, `pending_frames`), the age of the oldest of it
(`lag_ms`), and the log offsets committed and durable (`committed_offset`,
`durable_offset`; offsets restart with each epoch, `durable_epoch`).

## Configuration

| Option | Default | Meaning |
| --- | --- | --- |
| `:bucket` | required | Bucket name. |
| `:prefix` | `""` | Key prefix. One database per prefix. Leading, trailing and repeated `/` are dropped; characters such as `#` or `%` are percent-encoded in object names. |
| `:region` | `"us-east-1"` | AWS region. |
| `:endpoint` | AWS | For S3-compatible servers. Implies path-style URLs. |
| `:virtual_hosted_style` | path style with `:endpoint`, virtual-hosted otherwise | Force the URL style. |
| `:access_key_id`, `:secret_access_key`, `:session_token` | `AWS_*` environment variables | Credentials. |
| `:owner` | host/pid/random | Writer identity stored in the lease. |
| `:durability` | `:async` | `:async`: commits return once local, a background uploader stores them in order. `:sync`: every commit waits for its upload. See "Durability". |
| `:max_lag_ms` | `1_000` | Async: new commits wait while the oldest un-uploaded commit is older than this. |
| `:max_pending_bytes` | 16 MiB | Async: new commits wait while more log than this is not yet uploaded. |
| `:close_timeout_ms` | `10_000` | Async: how long closing waits for pending uploads (closing the last connection waits twice this at most). Commits still pending then are not durable. |
| `:lease_ttl_ms` | `30_000` | Lease duration (at least 1s). Renewed every third of it. |
| `:checkpoint_threshold` | turso's default (about 4 MB of log) | Log bytes between automatic checkpoints; each uploads a snapshot. `-1` disables automatic checkpoints. |
| `:request_timeout_ms` | `30_000` | Timeout per S3 request. Any single S3 operation, retries included, is also cut off after `request_timeout_ms * (max_retries + 1)`, so a store that stops answering fails commits instead of hanging them. |
| `:max_retries` | `3` | Retries per S3 request. |
| `:download_concurrency` | `32` | Parallel log downloads during restore. |
| `:mode` | `:writer` | `:replica` opens a read-only replica (see "Read-only replicas"). |
| `:group_commit` | `false` | Batch concurrent commits into one upload (see "Group commit"). |
| `:verify_conditional_writes` | `true` | Probe at open that the store enforces conditional writes (see [providers](s3_providers.md)). |
| `:incremental_snapshots` | `true` | Snapshots upload only what changed since the previous one (see "Checkpoints and snapshots"). |
| `:retain_epochs` | `0` | Earlier epochs (snapshot plus full log) kept for point-in-time restore. |

Give each process a stable `:owner`. A process that restarts with the same
owner takes its own lease over at once; with a random owner it has to wait
for the old lease to expire (one TTL). Never configure two live processes
with the same owner: they would take the lease from each other.

S3 databases always run in MVCC journal mode (`journal_mode: :mvcc` is
implied; any other journal mode is rejected). Switching it later with
`PRAGMA journal_mode` fences the writer: the statement returns an error,
every later write fails, and a reopen restores the S3 state. `:s3` can't be combined with
`mode: :readonly` (use `mode: :replica`) or `":memory:"`.

Several connections in one VM to the same path (for example a DBConnection
pool) share one S3 storage and one lease.

## What is guaranteed

**Durability of acknowledged commits.** A commit made with
`durability: :sync`, with `sync: true`, or before a successful
`Sediment.S3.flush/2` is stored in S3: a crash of the process or the
machine right after that loses nothing, and the next open restores it. With
async durability the other commits are restored if their upload finished,
and the restored state is always a prefix of the commit order.

The test suite checks this with a separate writer process that is killed
with SIGKILL mid-commit, three times in a row, against a real S3 server;
every commit it reported as done is restored (and at most the one commit in
flight at each kill, which it never reported). A longer crash-torture test
does the same for 30 minutes under injected faults (see "Crash testing").

**Failed uploads.** With sync durability, if storing a commit in S3 fails
(network error, timeout, lost lease), the statement returns an error and the
transaction is rolled back locally. With async durability the uploader
retries; if it is fenced or keeps failing past its retries, the writer is
poisoned: new commits fail, and `flush/2` and `sync: true` return an error
saying up to which log offset the data is durable. A pool reconnects and
restores that durable prefix once S3 is reachable (see "Failure modes").
Commits that were acknowledged but not yet uploaded are lost then, and the
loss is kept for the database file: `flush/2` and `sync: true` on writes keep failing
with `"s3 commits were lost: N acknowledged log frames never reached S3
(durable up to ..., committed up to ...)"`, on the reconnected pool too, and `info/1` shows it under
`lost`, until the application calls `Sediment.S3.acknowledge_loss/1`. So
a successful `flush/2` never covers commits that are gone.

**Ambiguous commits.** As with any remote database, a commit whose upload
reached S3 but whose answer was lost is reported as failed yet may be
durable. The writer detects this on its next commit, refuses further writes
(see "fenced" below) and must be reopened; the reopen restores that commit.
Applications that need exactly-once effects should make writes idempotent
or check after an error.

**One writer.** Only the lease holder writes. A second writer's open fails
with `"s3 lease held by <owner> until <unix ms>"`. A writer that stalls past
its lease (GC pause, network partition) can't damage the database: its
late uploads are either rejected by S3's conditional writes or ignored, and
none of its late commits are acknowledged.

**Clocks.** Safety never depends on clocks: the conditional writes fence a
stale writer whatever the clocks say. Availability during a takeover does:
the lease (its expiry is written by one node and read by another) assumes
node clocks agree to within `:lease_ttl_ms`. With a larger skew, two nodes
can each judge the other's lease expired and keep taking over, each fencing
the other, so neither serves until the skew is fixed (nothing is lost; the
TLA+ model finds exactly this livelock without the assumption). Keep node
clocks synchronized with NTP, or with HTTPS time sync (for example
`htpdate`) where UDP port 123 is blocked.

**Restore is verified.** The restored log must be contiguous and its CRC
chain must match; the snapshot's size and CRC are checked. Otherwise the
open fails with an `"s3 corrupt: ..."` error rather than silently dropping
data.

`Sediment.S3.info/1` reports the current epoch, snapshot, lease owner and
expiry, log offset, uploaded frames and bytes, whether the writer is
poisoned (fenced), the async queue (`pending_bytes`, `lag_ms`,
`durable_offset`) and any unacknowledged loss (`lost`).

## Failure modes

| Situation | What you see | What to do |
| --- | --- | --- |
| S3 unreachable during a commit | `durability: :sync` or `sync: true`: the statement returns an error; the transaction is rolled back. Async (default): the commit succeeds locally and waits only once the queue is full (`max_lag_ms`, `max_pending_bytes`); if uploads keep failing, the writer is poisoned and the queued commits are reported lost (row below). | Sync: retry the transaction once S3 is back. Async: nothing until the queue fills; use `sync: true` for writes that must not depend on it. |
| S3 unreachable for longer than the lease TTL | The lease lapses: every statement, reads included, fails as fenced (another writer may have taken over meanwhile, so the local copy can't be trusted). | With a pool: nothing, it reconnects and restores once S3 is back. Raise `:lease_ttl_ms` to ride out longer outages (a crashed writer then blocks others longer). |
| S3 unreachable during open | `{:error, "s3 store: ..."}` | Retry the open. |
| Another process holds the lease | Open fails with `"s3 lease held by ..."` | Wait for it to close or for the lease to expire, or use the same `:owner` when restarting the same process. |
| The lease was lost (renewal failed for longer than the TTL, or another writer took over) | Statements (reads too) fail with `"s3 writer fenced: ..."`; `info/1` shows `poisoned`. | With `Sediment.Connection` / Ecto: nothing; fenced connections disconnect (idle ones on their next ping) and reconnect with backoff, restoring from S3 as soon as no other writer holds the lease. With raw `Sediment.Engine`: close every connection to the path and reopen. |
| Async: the writer was fenced or closed with commits still queued | Those commits are gone; the pool reconnects from what is durable. `flush/2` and `sync: true` fail with `"... were lost ..."`; `info/1` shows `lost`. | Deal with the lost range (re-run the work, alert), then call `Sediment.S3.acknowledge_loss/1`. |
| A commit's answer was lost, then the upload landed | The next commit fails with a fenced error. | Reopen; the commit is restored. |
| Process or machine crash | Nothing synced or flushed is lost (with `durability: :sync`, nothing acknowledged). Async: the commits not yet uploaded are lost; the restore is a prefix of the commit order. | Reopen (on any machine). The lease must expire first unless the same `:owner` is used. |
| Local files deleted or corrupted | Nothing synced or flushed is lost. Async: commits not yet uploaded existed only in the local log and are lost. | Reopen; any local files at the path are replaced by the restore. |
| Objects deleted or damaged in S3 | Open fails with `"s3 corrupt: ..."` | Restore the bucket (for example from S3 versioning). |
| Empty prefix (new, cleared or mistyped) but a database with tables at the local path | Open fails with `"s3 config: ... refusing to replace the local file ..."`; the file is untouched | Check the bucket and prefix. To upload the file, `Sediment.S3.import/3`; to start empty, move or delete the local files. |
| `manifest.json` deleted but data objects remain | Open fails with `"s3 corrupt: no manifest.json but ..."` instead of creating an empty database over them | Restore the manifest, or clear the prefix to start over. |

Opening a prefix that holds a database always restores from S3 and replaces
the local files at the path; opening an empty prefix refuses to replace a
local database with tables. Don't point a non-S3 database and an S3
database at the same file.

## Timeouts

Each S3 request may take up to `request_timeout_ms` and is retried up to
`max_retries` times, so one request can take
`request_timeout_ms * (max_retries + 1)` (two minutes with the defaults),
and a commit makes up to three requests (PUT, then HEAD, plus a GET after a
failed PUT). `cancel/1`, DBConnection's `:timeout` (15 s by default) or the
owner process dying makes a commit that is waiting on S3 give up within
about 20 ms: the caller gets an
error and the connection disconnects. The upload may still land, so such a
commit is indeterminate, like any lost answer: acknowledged commits are
durable, and an abandoned one is either restored or rolled back.

With async durability a commit waits on S3 only when the upload queue is
full (`max_lag_ms`, `max_pending_bytes`); a timeout there cancels the
commit before anything is written. The disconnect then closes the
database, which first tries to upload what is queued, so the caller gets
its error once that gives up: up to twice `close_timeout_ms` after the
timeout while S3 is down.

A commit waiting on S3 (a `durability: :sync` upload, or an async commit
waiting for room in the queue) keeps a dirty IO scheduler thread for that
time, up to `request_timeout_ms * (max_retries + 1)`; the BEAM has 10 by
default, shared with file I/O. Busy-lock waits don't (they sleep in the
caller's process).

To bound commit latency, lower the S3 timeouts, for example
`request_timeout_ms: 5_000, max_retries: 2`, and keep the repo's `:timeout`
above roughly three times `request_timeout_ms * (max_retries + 1)`.

**Lock waits.** A writer holds the database write lock while its commit
uploads, and other writers wait in the busy handler, which polls rather
than queues: under contention some wait much longer than the average. S3
connections therefore default to `busy_timeout: 15_000` (instead of
`2000`). With many concurrent writers use `BEGIN CONCURRENT` (and
`group_commit`), whose commits don't hold the lock across the upload one by
one.

## Costs

Request counts per operation:

| Operation | S3 requests |
| --- | --- |
| Commit, `durability: :sync` | 1 PUT (the log frame) + 1 HEAD (ownership check); with `group_commit`, per batch of concurrent commits. Inside `BEGIN CONCURRENT`, each insert into an `AUTOINCREMENT` table adds one more (see below) |
| Commits, `durability: :async` | 1 PUT + 1 HEAD per uploaded segment: the commits made while an upload is in flight go into the next one (up to 8 MiB), so under load many commits share a request |
| `sync: true` or `Sediment.S3.flush/2` | nothing of its own: it waits for the uploads above |
| Checkpoint (automatic or `Sediment.S3.snapshot/1`) | 1 PUT (seal) + snapshot upload (a delta of the changed 64 KiB segments, or the whole database file; zstd-compressed, multipart above one part: 8 MiB parts, larger above about 70 GiB) + 1 PUT (manifest) + deletes of what no retained epoch references |
| Open | lease PUT, manifest GET/PUT, 1 GET per snapshot in the chain (at most 16), 1 LIST + 1 GET per log object, then a checkpoint (snapshot upload); the first writer open per VM also runs the conditional-write probe (4 PUTs + 1 DELETE) |
| Lease renewal | 1 PUT every `lease_ttl_ms / 3` |
| Close | 1 PUT (lease release) |
| Replica open or refresh | manifest GET, 1 GET per snapshot in the chain not cached from the last refresh, 1 LIST + 1 GET per log object; no writes |

At S3 Standard list prices in us-east-1 ($0.005 per 1,000 PUTs, $0.0004 per
1,000 HEAD/GET requests), sync-mode commits cost about $5.40 per million
(async ones at most that, and far less when they arrive faster than one
upload round trip, since they share segments), and lease
renewal with the default TTL about $0.04 per writer per day. Storage is
about one database file plus the log since the last checkpoint. Check
current pricing for your region.

To see what a workload actually sends, `Sediment.S3.request_counts/0`
returns the requests this OS process has made, per operation and price
class (retries and multipart parts included). With the environment variable
`SEDIMENT_S3_METER_DIR` set, every request is also appended to
`requests-<os pid>.log` there before it is sent (the log survives a crash),
and no request is sent while a `STOP` file exists in that directory: a
budget guard for load tests against a paid provider (`scripts/s3_soak.exs`
uses it).

Inside `BEGIN CONCURRENT`, turso_core allocates every `AUTOINCREMENT` id in
an inner transaction that commits on its own, so each such insert is a
commit of its own: 3 inserts in one transaction write 4 log frames instead
of 1 (with `durability: :sync`, 4 uploads, each waited for; with `:async`
they are queued and share segments). Plain `BEGIN` transactions and tables
with `INTEGER PRIMARY KEY` (no `AUTOINCREMENT`) are not affected. For S3
databases with concurrent writers, prefer `INTEGER PRIMARY KEY` (in
ecto_sediment: `migration_primary_key: [type: :integer]`).

Restore time grows with the log since the last checkpoint: on a local
SeaweedFS server, restoring 500 log objects took 0.29 s and 2,000 took
0.85 s (32 parallel GETs), plus the snapshot download. Keep
`:checkpoint_threshold` moderate if fast opens matter.

Latency: with `durability: :sync` (or `sync: true`) a commit waits for the
PUT and the HEAD in sequence; against AWS S3 expect the sum of two in-region
request latencies per commit. With async durability commits don't wait, and
contiguous commits may share one upload. Batch
writes in transactions: a transaction costs one commit however many rows it
writes (1,000 inserts in one transaction took 51 ms locally).

Measured (see "Testing and measurements"): an async commit costs what a local one does; `sync: true` costs about what a sync-mode
commit does, so an application pays for durability only where it asks for it.

Tables with an `AUTOINCREMENT` key (Ecto's default primary key) gain little: in MVCC
mode turso_core itself spends about 10 ms on a 100-row insert into such a table, with or
without S3 (0.3 ms with a plain `INTEGER PRIMARY KEY`), so that local cost dominates
either durability mode. Use integer primary keys for write-heavy tables
(`migration_primary_key: [type: :integer]` in ecto_sediment).

Group commit always cuts the requests (8x fewer objects with 16 writers).
It raises throughput when uploads are slow relative to local work (4.3x on
MinIO at 16 writers). With one writer it changes nothing.

Each retained epoch (`retain_epochs`) keeps one more snapshot plus its log.

A full snapshot uploads the whole database file, zstd-compressed (level 3)
and streamed in multipart parts (8 MiB; above about 70 GiB the parts grow
with the database so a snapshot always fits in S3's 10,000 parts, up to its
5 TiB object limit), buffering one part at a time; most checkpoints upload only a delta (see "Checkpoints and
snapshots"). Text-heavy databases typically shrink severalfold; encrypted
databases don't compress. A 105 MiB incompressible database took 3.2 s to
checkpoint and upload and 1.5 s to restore on a local SeaweedFS (13 parts). For large databases raise
`:checkpoint_threshold` so this happens less often; the cost is a longer log
to replay on open.

## Read-only replicas

Any number of processes can read the database without the lease:

```elixir
{:ok, replica} =
  Sediment.Engine.open("/var/lib/app/replica.db",
    s3: [bucket: "my-bucket", prefix: "prod/app", mode: :replica],
    encryption: encryption
  )

# later, to catch up with the writer
{:ok, %{epoch: _, log_bytes: _}} = Sediment.S3.refresh(replica)
```

A replica restores the current snapshot and log (verified like a writer's
restore), opens them read-only and never writes to S3. It shows the state
as of its last restore; `Sediment.S3.refresh/1` downloads the latest
state and reconnects (statements prepared before are finalized). Call it on
a timer if the replica should follow the writer. A replica can also be
opened through `Sediment.start_link/1` or Ecto. The connections to one
replica in a VM share one working copy (`.<name>.replica-<pid>-<n>.db` next
to the given path): a refresh restores the latest state once, and the other
connections switch to it at their next refresh without S3 requests (a
pool-wide refresh asks them to). A copy is removed when its last connection
has moved on or closed.

A replica keeps the snapshot it last restored (before the log) next to the
given path (`.<name>.s3-cache-<hash>`, one copy of the database), so a
refresh downloads only the snapshot deltas published since, plus the log.
The rebuilt file is checked against the manifest like a full download, and
a missing or damaged cache just means a full download.

`Sediment.S3.refresh/1`, `info/1` and `snapshot/1` also take a pool:

```elixir
{:ok, replica} = Sediment.start_link(database: "/var/lib/app/replica.db",
  s3: [bucket: "my-bucket", prefix: "prod/app", mode: :replica], encryption: encryption)

{:ok, _info} = Sediment.S3.refresh(replica)
```

The connection that runs the call refreshes at once; every other connection
of the pool refreshes before its next statement outside a transaction.

A replica may briefly show a commit whose writer later reports it as failed
(an ambiguous commit, see "What is guaranteed"): such a commit is durable, and the writer's
next open restores it too.

## Importing an existing database

`Sediment.S3.import/3` uploads an existing database file, written by SQLite
or Sediment, as the first state of an empty prefix:

```elixir
# with every writer of the file stopped
{:ok, %{objects: 12, rows: 48_210, sequences_not_advanced: []}} =
  Sediment.S3.import("/var/lib/app/app.db", s3, encryption: encryption)

# then, as usual (the open restores the imported database over the file)
{:ok, db} = Sediment.Engine.open("/var/lib/app/app.db", s3: s3, encryption: encryption)
```

The file and its WAL are copied next to it (mode 0600) and read from that
copy. The schema and rows are copied into a new MVCC database: rowids,
AUTOINCREMENT sequences (also above the largest id when the newest rows were
deleted), indexes, views, triggers, foreign keys and `user_version`. The new
database is checked (row counts, `PRAGMA integrity_check`) and uploaded as
the first snapshot under the writer lease, with the same create-only
manifest write that creates a new database. The source is never written
to, and the temporary files are deleted whatever happens. Nothing in S3 is
used until that manifest write, so a failed import (or a process killed
during one) can simply run again; what it uploaded before is collected
later.

A logical copy rather than switching the file to MVCC: in turso_core 0.8.1
that switch breaks AUTOINCREMENT tables (the next insert reuses id 1 and
overwrites the row; files written by SQLite can't insert into them at all).

* `verify: :checksum` (the default) checks the stored snapshot's size and
  CRC32C against the new file (every part also carries a SHA-256 the store
  checks); `verify: :restore` also downloads the database and compares.
* `encryption: [cipher: ..., key: ...]` encrypts the new database (open it
  with the same `:encryption`). An encrypted source needs its key as
  `source_encryption:`. SQLCipher files can't be read.
* The prefix must be empty: an import into a prefix that holds a database
  fails with `"... already holds a database ..."`.
* MVCC doesn't support WITHOUT ROWID tables and virtual tables (such as
  fts5; Turso has FTS indexes instead), so files with them are refused, and
  so are files with a hot rollback journal. Fix them with SQLite first.
* AUTOINCREMENT sequences carry over, also for tables whose newest rows
  were deleted and for emptied tables (with UNIQUE columns and NOT NULL
  timestamps, as Ecto makes them). An emptied table whose CHECK
  constraints refuse a placeholder row (zero, empty text, empty blob) can't
  be advanced: its ids start again at 1, the result lists it in
  `sequences_not_advanced`, and a warning is logged.
* A snapshot must fit in one S3 object (5 TiB, compressed); larger files
  are refused. The import needs about twice the file's size
  free next to it.
* Speed: AUTOINCREMENT tables (every Ecto table) copy at about 5,000 to
  7,000 rows/s, whatever the row size (measured from 20 bytes to 1 KB per
  row); other tables at about 25 MB/s, or 100,000 rows/s for small rows. In
  turso_core 0.8.1 each AUTOINCREMENT insert under MVCC also updates the
  table's sequence, so the copy commits every 500 rows and checkpoints every
  1,000 to keep that cost flat. The upload adds the time to send the
  compressed file. For a database of mostly Ecto tables, plan about 4
  minutes of downtime per million rows, plus the upload (measured on a local
  disk against an in-memory store; time it first by importing a copy of the
  file into a scratch prefix, then delete that prefix). The application pays
  the same per-insert sequence cost for AUTOINCREMENT tables after the
  import.
* Requests: a few for the probe, lease and manifest, plus one per part
  (8 MiB up to about 70 GiB) (a 10 GiB database is about 1,300 PUTs).

With Ecto, `mix ecto.sediment.s3.import` runs it with the repo's
configuration (see ecto_sediment's S3 guide).

## Point-in-time restore

With `retain_epochs: n`, the writer keeps the last `n` epochs when it
collects garbage. An epoch is the snapshot taken at a checkpoint plus every
commit until the next one, so the retained window reaches back `n`
checkpoints. `Sediment.S3.restore/3` rebuilds the database as of a
moment in that window into a standalone local file. It doesn't take the
lease or write to S3, so it's safe to run next to a live writer:

```elixir
{:ok, info} =
  Sediment.S3.restore("/tmp/before-the-migration.db", s3_opts,
    at: ~U[2026-09-29 21:00:00Z]
  )

{:ok, db} = Sediment.Engine.open("/tmp/before-the-migration.db")
```

`at:` picks the newest retained epoch that started by then, and replays
its commits whose upload landed by then (S3's `last_modified`). The cutoff is
only as precise as `last_modified`, which S3 and most compatible servers
report in whole seconds, and compares it with your clock: allow a second
or two (plus any clock skew) around the moment you ask for. Keep the clock
synchronized: on a host whose clock ran 4 minutes behind, every commit of the
last minutes looked newer than the moment asked for, and the restore found
none of them. `epoch: n`
restores the start of epoch `n` plus its whole log, and no option restores
the latest state. Asking for a moment outside the window returns an error
that lists the retained epochs. The restored file is an ordinary database;
to make it the S3 database again, copy its data into a fresh prefix. The
S3 prefix itself isn't rolled back.

## Encryption

S3 databases are encrypted by default. Every open with `:s3` (a writer, a
replica), `Sediment.S3.restore/3` and `Sediment.S3.import/3` needs one of:

```elixir
# a key: 32 random bytes as 64 hex characters
encryption: [cipher: "aegis256", key: Sediment.S3.generate_key()]

# or the explicit choice to store the database unencrypted
encryption: false
```

Without either, they fail before writing anything, and the message says what
the prefix holds:

| The prefix holds | Error |
|---|---|
| nothing yet | `"s3 config: S3 databases are encrypted by default: set encryption: [...] ..., or encryption: false ..."` |
| an unencrypted database | `"s3 config: the database at this S3 prefix is unencrypted: open it with encryption: false ..."` |
| an unencrypted database, opened with a key | `"s3 config: the database at this S3 prefix is unencrypted: open it with encryption: false ..."` (nothing is written; to encrypt it, import it into a new prefix) |
| an encrypted database (also with `encryption: false`) | `"s3 config: the database at this S3 prefix is encrypted: open or restore it with the :encryption option it was created with"` |

Generate the key once per database (`Sediment.S3.generate_key/0` or
`openssl rand -hex 32`) and keep it with your other secrets, for example in
a `DATABASE_ENCRYPTION_KEY` environment variable: every restore needs it,
and without it the data can't be read. An existing unencrypted database
stays unencrypted (open it with `encryption: false`); to encrypt one, import
its data into a new prefix with `Sediment.S3.import/3` and a key.

Connections to a database already open in the VM (more connections of a
writer or a replica, a plain open of a writer's file) share its decrypted
state, so each must give the same choice: the same key, or `encryption:
false` for an unencrypted one. A missing or different key is refused.

A writer open with a wrong key takes the lease and records itself as the
manifest's writer before the restore finds the key wrong, then releases the
lease. Nothing in the database changes, and the next open with the right key
proceeds normally.

The bucket then holds only ciphertext. Snapshots are the encrypted database
file, and every log frame is encrypted by turso's logical log (32 KiB chunks,
each with its own nonce and tag); a restore checks the log's integrity
without the key. The manifest and lease are plaintext metadata (epoch numbers,
object names, writer identity). Every restore needs the same `:encryption`
option: a writer's open, a replica, and `Sediment.S3.restore/3` (whose
output file stays encrypted). A wrong or missing key fails with
`"...can't be read with the given encryption options (wrong key, ...)"`
after the download. The key never goes to S3, and the conditional-write
probe doesn't need it.

## Group commit

With `durability: :sync` every commit is its own upload (async durability
already coalesces contiguous commits). With concurrent writers (MVCC
and `BEGIN CONCURRENT`, several connections), `group_commit: true` uploads
all transactions that commit together as one object: Turso already groups
their local log writes, and the batch is uploaded once before any of them is
acknowledged. In a test with 8 writers and 20 ms uploads, 160 commits needed
39 objects instead of 160.

The trade-offs:

* The connections are held at `synchronous = FULL` (Turso only runs the
  step that uploads the batch for FULL commits). `PRAGMA synchronous` and
  the `:synchronous` connection option are overridden.
* A failed upload can't roll back just one transaction: Turso has already
  advanced its log past the batch. The writer is fenced (commits fail with
  "a group commit could not be stored in S3 ... reopen the database") and
  must be reopened; the reopen restores whatever reached S3. Until then,
  reads on its connections fail too, because Turso's memory still holds the
  lost batch. A pool does the reopen by itself: each connection disconnects
  on the error and reconnects once S3 is reachable. Handles from
  `Sediment.Engine.open/2` must be closed and reopened by you. Without
  group commit, a failed upload only fails that commit.

Sequential commits from one connection gain nothing from it.

## Checkpoints and snapshots

A checkpoint folds the log into the database file and uploads a snapshot for
the next epoch. With `incremental_snapshots: true` (the default) that
snapshot is a delta: only the 64 KiB segments of the file that changed since
the previous snapshot, zstd-compressed. The manifest names the chain, a full
snapshot followed by deltas, and a restore downloads and applies it, then
checks the rebuilt file's size and CRC32C like a full snapshot's. A
checkpoint compares segment hashes of the local file, so it reads the whole
file from local disk but uploads only what changed.

Uploaded per checkpoint for a 40 MB database of 64 KiB blobs (incompressible),
after changing some rows (`cargo test --release incremental_snapshot_sizes_probe
-- --ignored`):

| Rows changed | Full snapshot | Incremental |
| --- | --- | --- |
| 1 | 41,329 KB | 192 KB |
| 10 | 41,333 KB | 707 KB |
| 100 (6.4 MB of data) | 41,333 KB | 6,530 KB |

The next snapshot is full again when the chain has 16 links, when more than
half of the file changed, or when the deltas add up to more than the full
snapshot; so a restore downloads at most about 2.5 times the compressed
database.
Objects that no retained epoch's chain references are deleted.

turso stops every read and write on the database while a checkpoint runs,
so the checkpoint itself does no S3 work: it waits for the async upload
queue (at most 10 s, otherwise it gives up and runs later) and copies the
database file (time proportional to its size), then returns. Uploading the
snapshot and the manifest, and deleting old objects (in batches: S3's
DeleteObjects takes 1,000 keys per request), happen in the background
afterwards. Until the snapshot is published, commits keep working; with
`durability: :sync` the first one publishes it before its own upload.

A manifest has version 2 while its snapshot, or the snapshot of any epoch it
retains for point-in-time restore, is a chain. A sediment version from before
incremental snapshots refuses them (`unsupported manifest version 2`); set
`incremental_snapshots: false` while such versions may still open the
database.

## Providers

Any S3-compatible store that enforces conditional writes
(`If-None-Match: *` and `If-Match` on PUT) works: AWS S3, MinIO, SeaweedFS,
Cloudflare R2, Tigris. A writer checks this with a probe when it opens and
refuses to run on a store that ignores them. See the
[provider guide](s3_providers.md).

## Limitations

* Every open downloads the snapshot chain and uploads a fresh snapshot (a
  delta when little changed).
* Point-in-time restore covers only the retained epochs, and restores into
  a local file; the S3 database itself can't be rolled back in place.
* A database file reached through a symlink is the same database as its
  target; a hard link to an S3 database file is not supported (a restore
  replaces the file, leaving the link behind).
* A replica's refresh downloads the newer snapshot deltas and the whole log
  of the current epoch; after a full snapshot, the whole snapshot again.
* A database's snapshot must fit in one S3 object: 5 TiB compressed. Up to
  about 70 GiB it goes up in 8 MiB parts; above that the parts grow (to
  about 590 MiB at 5 TiB), and so does the memory an upload buffers (one
  part).

## Testing and measurements

### Crash testing

`mix test --only torture` (30 minutes; `TORTURE_MINUTES` to change) runs a
writer as a separate BEAM (`test/support/torture_writer.exs`): three tasks
commit autocommit inserts and 1 to 3 row transactions (`BEGIN` and
`BEGIN CONCURRENT`), a fourth takes snapshots at random intervals, and the
checkpoint threshold is low, so checkpoints run constantly. Every third run
uses group commit, and some runs take over from a different owner. It talks
to S3 through a proxy that delays requests and responses (up to 100 ms) and
resets connections (up to 20% of them), so uploads fail, time out, or land
without an answer. The writer is killed with SIGKILL while it opens, at a
random time, or just after a snapshot starts. After every kill the database
is restored from S3 into a fresh directory (which checks the log's CRC chain
and the snapshot chain) and checked:

* every transaction ever acknowledged is there, all of its rows;
* a transaction that failed with a conflict left no row;
* a transaction that was in flight or failed ambiguously left all of its
  rows or none;
* every row holds the values its transaction wrote, and belongs to a
  transaction a writer reported;
* every row a restore has shown stays there.

The first run is killed right after the empty database is published, before
the table exists. Some runs play a zombie instead: the writer is paused
(SIGSTOP) past its lease, a second writer (the same owner, or another one
once the lease expired) takes over and commits, then the first one runs
again for a few seconds before both are killed. The resumed writer's commits
fail as fenced; any it acknowledged would have to be in the second writer's
database.

Results (SeaweedFS unless noted):

| Run | Kills (open / random / mid-snapshot) | Acknowledged rows verified | Violations |
| --- | --- | --- | --- |
| Full snapshots, 30 min | 265 (51 / 95 / 119) | 53,022 | 0 |
| Incremental snapshots, 30 min | 279 (60 / 99 / 120) | 54,198 | 0 |
| Incremental, transaction and value checks, 30 min | 223 (41 / 94 / 87, + 1 at bootstrap) | 56,167 | 0 |
| Same plus zombie writers, on MinIO, 30 min | 242 (41 / 92 / 73, + 35 zombies, 1 at bootstrap) | 44,608 | 0 |

In the second run the database ended at 14 MB with a chain of a full
snapshot and 8 deltas, so restores after the kills rebuilt chains.
Unacknowledged rows found durable (in-flight or ambiguous commits that had
landed): 267, 250 and 226. The first two runs checked rows by id only; the
third checks whole transactions and row values. Transactions in `BEGIN CONCURRENT` also
sometimes failed with `"Write-write conflict"` although their rows differ;
those failures are safe (the rows never appear) and are retried by the
application.

#### Multi-node, 12 hours on Tigris

A 12-hour soak ran on three boat.dev sandboxes (its controller, workload app and oracle live
outside this repository; the oracle restored both prefixes into fresh directories and checked
them against every node's ledger of acknowledged, synced and flushed commits) (4 vCPU, EU) against Tigris, with an Ecto app.
Nodes a and b were writers on one prefix, arbitrated by the lease. Node c ran a replica of that
prefix (refresh every 30 s) and a growth writer on its own prefix (1 row/s of 64 KiB, about 2.2 GB
written). The load was 2 transactions/s, 10 % of them `sync: true`, with a flush every minute.

A controller ran 53 chaos events: 12 kill -9s of the active writer, 16 partitions from S3 (11 s to
3 min), 9 rolling deploys, 8 graceful restarts, 6 clock skews (3 within the lease TTL, 3 beyond it),
and 2 quiet periods. Every 30 minutes it restored both prefixes and checked the ledgers:

- **23 checks, 0 violations.** 76,136 commits on the shared prefix and 34,370 on the growth prefix.
  Every `sync: true` and flushed commit was present, acknowledged async commits formed a prefix per
  incarnation, there were no partial transactions, and everything the replica showed stayed.
- The waiting writer took over after every kill, partition and deploy. The skews beyond the TTL
  caused no takeover duel (but keep clocks synchronized, see above).
- **A sustained outage costs the async tail.** During node c's 75 s and 172 s partitions, the growth
  writer's uploader gave up (after its retries) and reported the commits not yet uploaded as lost.
  `flush/2` and `sync: true` then failed until `acknowledge_loss/1`. Commits that were synced or
  flushed were never lost. Use `sync: true` for writes that must survive an outage.
- **Cost: $1.58 in S3 requests for 11.7 hours, about $3.25 a day** at this load (Tigris prices).
  Two thirds of it was the replica: each refresh re-reads every log object of the writer's current
  epoch (1.7 M GETs), so a replica costs up to `refreshes x log objects since the last checkpoint`.
  Refresh less often, or lower the writer's `:checkpoint_threshold`, to cut it.
